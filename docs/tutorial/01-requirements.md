# 第 1 章　需求分析

## 學習目標

- 把一份文字需求分類成功能需求、非功能需求、限制與假設。
- 把客戶的口語描述轉成可以量測的工程指標。
- 找出需求中模糊或互相矛盾的地方，提出選項並取得決定。
- 寫出「可以被測試證明」的驗收標準，並建立需求追溯表。

---

## 1.1 原始需求

需求來自一份案件說明。客戶是一間兩人經營的顧問工作室：

> 電腦裡累積了十幾年、約十萬個 Word、純文字、CSV 與 HTML 檔，其中不少是舊版的 Big5 編碼檔。Windows 內建搜尋對中文常找不到、舊檔顯示亂碼，她們想要一個能秒搜中文與英文、標出命中位置、檔案一存檔就能搜到的桌面工具。

這段話只有四句，卻已經包含了大部分的核心需求：

| 客戶的說法 | 背後的需求 |
|---|---|
| 十萬個檔案 | 規模：索引要能處理 10 萬份文件 |
| Word、純文字、CSV、HTML | 要支援多種檔案格式的文字抽取 |
| 舊版 Big5、顯示亂碼 | 要能偵測文字編碼 |
| 對中文常找不到 | 中文分詞是核心問題 |
| 秒搜 | 查詢延遲要很低 |
| 標出命中位置 | 要能把命中位置對應回原始文字 |
| 一存檔就能搜到 | 要監看檔案變更，並增量更新索引 |

**教學重點**：需求分析的第一步不是寫程式，而是**把每一句話問到底**。「秒搜」是多快？「十萬個檔案」平均多大？「存檔就能搜到」是幾秒內？說明書的後半段把這些都量化了，但在真實專案中，常常要由分析師主動去問。

---

## 1.2 需求的分類

### 利害關係人

| 角色 | 關心的事 |
|---|---|
| 使用者（工作室的兩位成員） | 找得到、找得快、結果正確、不會當機 |
| 驗收者（出題者） | 26 項驗收標準是否都能被證明 |
| 未來的維護者 | 程式是否看得懂、改得動、有測試保護 |

### 功能需求（Functional Requirements）

把說明書中的功能整理成編號清單，方便後續追溯。下面是節錄：

| 編號 | 需求 |
|---|---|
| FR-1 | 設定多個根資料夾與排除規則（glob），可暫停與恢復索引 |
| FR-2 | 支援 .txt、.md、.csv、.log、.json、.xml、.html、.htm、.docx |
| FR-3 | 偵測 UTF-8（有無 BOM）、UTF-16（有 BOM）、Big5；判定不出就跳過並記錄原因 |
| FR-4 | HTML 略過 script 與 style 並解碼實體；docx 只取內文段落 |
| FR-5 | 爬檔要承受接合點迴圈、長路徑、鎖定檔、權限不足、讀取中被修改 |
| FR-6 | 查詢語言：詞、片語、AND、OR、NOT、括號、前綴、篩選條件 |
| FR-7 | 語法錯誤時顯示位置與說明，不崩潰 |
| FR-8 | 依 BM25 變形排序，檔名命中加倍，回傳前 K 筆與總數 |
| FR-9 | 監看新增、修改、改名、移動、刪除；改名不重新分詞 |
| FR-10 | 輸入即搜尋，新查詢取消舊查詢；預覽顯示摘要與高亮 |
| FR-11 | 狀態列、診斷頁、設定存成 JSON |

### 非功能需求（Non-Functional Requirements）

| 類別 | 需求 | 量化指標 |
|---|---|---|
| 效能 | 建立索引 | 5 萬份、平均 20 KB，≤ 4 分鐘 |
| 效能 | 查詢延遲 | 兩詞 AND 與片語的 P95 ≤ 100 ms |
| 效能 | 開啟索引 | ≤ 2 秒 |
| 效能 | 記憶體 | 峰值 ≤ 600 MB |
| 效能 | 存檔到可搜尋 | ≤ 3 秒（含防抖） |
| 可靠性 | 中斷安全 | 任何時間點中止後重開，索引一致，不需手動修復 |
| 可靠性 | 損毀處理 | 版本不符或片段損毀時明確提示，只重建受影響部分 |
| 使用性 | 鍵盤操作 | Ctrl+K、方向鍵、Enter、Alt+Enter |
| 回應性 | 取消 | 取消查詢在 50 ms 內生效 |

**教學重點**：「P95」比「平均」更能反映使用者的感受。平均 10 ms 的系統，如果每 20 次就有一次 2 秒，使用者會覺得它「常常卡住」。

### 限制（Constraints）

限制不是功能，而是**解法的邊界**。這個專案的限制特別多：

- 技術棧：C#、.NET 9、Uno Platform，只以 Windows 為目標。
- 專案切分：Core、Indexing、App.ViewModels、App 四個專案，前三個必須是純 `net9.0`，不得引用 UI。
- **不得使用現成的全文檢索程式庫**（Lucene.NET、SQLite FTS 等），索引格式要自己設計。
- 所有索引檔的 I/O 必須經過一個介面，以便在測試中注入故障。
- 所有「現在時間」必須透過 `TimeProvider`。
- 分數用 `double` 計算，但長度、詞頻、文件頻率、文件數必須以整數保存。
- 測試用 xUnit；參考解必須獨立實作，不得共用分詞或計分程式碼。

前三條決定了技術選擇；後四條其實是**對可測試性的要求**。出題者用限制的形式，強迫設計者把測試需要的接縫（seam）留在架構裡。第 3 章會看到這些限制如何直接變成介面。

### 假設事項（Assumptions）

說明書最後有一大段「假設事項」，精確定義了正規化、分詞、查詢語意與計分公式，例如：

> 正規化：先做 Unicode NFKC，再轉小寫（invariant），最後將 臺 轉為 台。
> 連續的 CJK 區段長度為 L：L ≥ 2 時產生 L − 1 個重疊雙字詞元，L = 1 時產生一個單字詞元。

這類規格看起來囉嗦，但非常重要：它讓「正確答案」變成唯一，才有可能寫出參考解，並逐字比對結果。沒有這些定義，「搜尋結果正確」根本無法驗證。

## 1.3 從客戶語言到工程語言

需求分析最常見的失敗，是把模糊的形容詞直接帶進設計。下表是本專案的轉換：

| 客戶語言 | 工程語言 | 驗證方式 |
|---|---|---|
| 秒搜 | 兩詞 AND 與片語 P95 ≤ 100 ms | 效能工具量 300 條查詢 |
| 存檔就能搜到 | 存檔後 ≤ 3 秒可被搜尋 | 效能工具寫檔後輪詢查詢 |
| 舊檔顯示亂碼 | 嚴格 Big5 解碼；判定不出就跳過並記錄 | 單元測試 + 範例語料 |
| 標出命中位置 | 每個詞元都能對應回原始文字座標 | 性質測試 |
| 結果要對 | 命中集合與分數和參考解一致（誤差 ≤ 1e-9） | 性質測試 |

## 1.4 處理模糊與矛盾：決策點

即使說明書寫得很詳細，開發前的分析仍然找到六個需要決定的地方（決策 A 到 F）。處理方式是固定的：**列出選項、說明影響、提出建議、請需求方確認**。以下挑三個最有教育意義的。

### 決策 A：數學上不可能的需求

驗收標準 #2 要求：「每個詞元對應回原始文字的位置範圍，取出的子字串正規化後等於該詞元」。

但考慮字元 `㈱`：NFKC 會把它變成三個字元 `(株)`，產生的詞元是 `株`。把 `㈱` 取回來再正規化，得到的是 `(株)`，不等於 `株`。所以「等於」對所有輸入**不可能成立**。

分析時提出的精確定義：

- (a) 取出的子字串正規化後**包含**該詞元；
- (b) 範圍是**最小的**；
- (c) 若詞元的每個字元都來自獨立的原始字元，則**完全相等**（涵蓋全形字、代理對與一般文字）。

**教學重點**：遇到不可能的需求，不要默默挑一個解釋就做下去，也不要假裝它可行。要舉出反例、提出最接近原意的可驗證版本，並取得同意。

### 決策 B：「只有 NOT 的查詢被拒絕」是什麼意思？

`-b` 顯然只有 NOT，那 `a OR -b` 呢？`NOT NOT a` 呢？`-ext:txt` 呢？

如果只檢查「根節點是不是 NOT」，會漏掉 `a OR -b`。這個查詢等於「含 a 或不含 b 的所有文件」，幾乎就是全部文件，和只有 NOT 一樣沒有意義。

分析時提出用**有界性**（boundedness）來定義：

- 詞項、片語、篩選條件是有界的；
- `NOT x` 是無界的；
- `AND` 只要有一個子節點有界就有界；
- `OR` 所有子節點都有界才有界。

根節點必須有界，否則拒絕。這個定義有清楚的數學意義（結果集合是否被某個正向條件限制住），也容易寫成測試。第 5 章會看到它的實作，以及實作時發現的一個錯誤。

### 決策 E：照規格做，但結果可能違反直覺

規格說 glob 比對的是「相對於根資料夾的完整路徑」，而 `*` 不跨越 `/`。照字面實作，`*.tmp` 只會排除根目錄下的 `.tmp`，子資料夾裡的不會被排除；要全部排除得寫 `**/*.tmp`。

這和 `.gitignore` 的習慣不同。分析時列出兩個選項（嚴格照規格，或仿 `.gitignore`），建議**嚴格照規格**，並在設定頁提示使用者。理由是規格是驗收依據，而這個差異可以用說明文字彌補。

### 其他決策

| 決策 | 內容 | 採用的方案 |
|---|---|---|
| C | 接合點與符號連結 | 跟隨，但用 canonical 路徑去重；目標在根資料夾內的連結略過 |
| D | 隱藏與系統檔 | 預設略過（例如 Office 暫存檔 `~$x.docx`），設定可關閉 |
| F | 引入哪些套件 | System.IO.Hashing、TimeProvider.Testing、CommunityToolkit.Mvvm |
| 其他 | 「檔名詞頻乘 2」是否套用到片語、前綴、單字詞頻 | 一律套用 |
| 其他 | 搜尋框防抖時間 | 150 ms |
| 其他 | 摘要長度以什麼計算 | 以 UTF-16 char 計，但不切斷代理對 |

完整的決策紀錄在 [architecture.md](../architecture.md) 中以 🔶 標示。

## 1.5 驗收標準：讓需求可以被證明

說明書列了 26 項驗收標準，每一項都附上**判定方式**。節錄如下：

| # | 標準 | 判定方式 |
|---|---|---|
| 1 | 分詞結果與預期檔逐項一致 | 單元測試 |
| 5 | 至少 300 份隨機文件、2000 條隨機查詢，命中集合與參考解完全一致 | 性質測試 |
| 12 | 內容未變的改名不觸發重新抽取與分詞（以計數器斷言） | 單元測試 |
| 15 | 在提交與合併的每一個 I/O 操作注入故障，重開後一致 | 故障注入測試 |
| 20 | 取消在 50 ms 內生效 | ViewModel 測試（假時鐘與假排程器） |
| 22 | 效能符合限制，並在 README 載明測量環境 | 效能測試＋實測 |

好的驗收標準有三個特徵：

1. **可觀察**：有明確的輸入與預期輸出。「改名不重新分詞」本來無法從外部觀察，所以加上「以計數器斷言」，讓它變得可觀察。
2. **有判定方式**：寫明要用哪一種測試證明，避免事後爭論「這樣算不算通過」。
3. **涵蓋邊界**：例如 #8 明確要求「剛好等於、差一單位、大小寫、時區換日」。

### 需求追溯表

開發時把每一項驗收標準對應到具體的測試類別，維持一張**追溯表**（traceability matrix）。本專案的追溯表在 README 第 10 節與 [test-report.md](../test-report.md) 第 5 節，節錄如下：

| # | 測試 |
|---|---|
| 1 | `Text/TokenizerExpectedFileTests` + `TestData/tokenizer-expected.json` |
| 5、6、7、9 | `Properties/SearchProperties` |
| 12 | `Pipeline/IndexingEngineTests`（改名、移動、資料夾改名的計數器斷言） |
| 15 | `Index/FaultInjectionTests` |

追溯表讓「完成了沒」變成可以逐列檢查的事實，也讓任何一個測試失敗時，都能立刻知道影響哪一項需求。

## 1.6 需求分析的盲點：一個真實案例

需求寫著「偵測 Big5」。開發時的實作是：先試嚴格 UTF-8，失敗再試嚴格 Big5，兩者都失敗就跳過。單元測試全部通過，驗收也通過。

上線前的審查卻發現：**簡體中文的 GBK 檔案，位元組結構剛好也是合法的 Big5**。這種檔案會被當成 Big5 解碼，索引成一堆亂碼（例如「这是一份简体中文的报告」變成「涴岆珨爺潠极笢恅腔惆豢」），使用者永遠搜不到，診斷頁也不會顯示它被跳過。

需求沒有提到 GBK，但客戶的情境（十幾年的檔案、同時有簡繁文件的工作室）讓這件事很可能發生。這說明了兩件事：

- 需求文件寫的是「要做什麼」，但**使用情境**決定了「做到什麼程度才算對」。
- 已知限制要誠實寫出來。開發時已在 README 列出「Big5 可能誤判 GBK」，審查者才能據此評估風險。

第 9 章會說明如何用實驗數據決定修正的門檻。

## 練習

1. 從原始需求中再找出三個形容詞或口語描述，把它們轉成可以量測的指標。
2. 用有界性的定義判斷下列查詢是否合法：`a -b`、`-b`、`a OR -b`、`NOT (NOT a)`、`-ext:txt`、`ext:txt`、`(a OR b) -c`。寫完後對照 `tests/LocalSeek.Tests/Query/QueryBinderTests.cs` 檢查答案。
3. 驗收標準 #12 為什麼要「以計數器斷言」？如果不加這句，你會怎麼驗證「改名不重新分詞」？
4. 想一個這份需求沒有提到、但真實使用時可能遇到的情境（類似 GBK 的例子），說明它會造成什麼問題。
