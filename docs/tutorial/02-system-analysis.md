# 第 2 章　系統分析

## 學習目標

- 畫出系統脈絡圖，界定系統的邊界與外部實體。
- 用使用案例描述系統的行為。
- 建立領域模型，找出系統中真正的「名詞」與它們的關係。
- 描述主要資料流與狀態變化。
- 從需求中找出**會決定架構的難點**，並評估風險。

需求分析回答「要做什麼」；系統分析回答「這個系統由哪些東西組成、它們怎麼互動」。這一章的產出，是第 3 章架構設計的輸入。

## 2.1 系統脈絡

```
 ┌──────────── 使用者（顧問工作室，2 人，單機）────────────┐
 │  輸入查詢 / 瀏覽結果 / 開啟檔案 / 設定根資料夾 / 看診斷 │
 └──────────────────────────┬──────────────────────────────┘
                            │
                   ┌────────▼────────┐        ┌──────────────────────┐
                   │   LocalSeek App │◄──────►│ %LocalAppData%\       │
                   │  (Uno, Windows) │        │   LocalSeek\          │
                   └────────┬────────┘        │   settings.json       │
                            │ 讀取 / 監看      │   index\ (自製格式)   │
             ┌──────────────▼──────────────┐  └──────────────────────┘
             │ 使用者的根資料夾（本機 / 網路磁碟）│
             │ ~10 萬個 txt/md/csv/log/json/xml/│
             │ html/htm/docx，含 Big5 舊檔      │
             └─────────────────────────────────┘
```

脈絡圖的價值在於**畫出邊界**：

- 系統**讀取**使用者的檔案，但**從不修改**它們。
- 系統**擁有** `%LocalAppData%\LocalSeek\` 底下的設定與索引，可以任意寫入、刪除、重建。
- 開啟檔案、在檔案總管中顯示，是交給作業系統的外部動作。

邊界決定了錯誤處理的策略。使用者的檔案是不可控的外部資料：可能被鎖住、被刪除、編碼錯誤，處理方式是「記錄後略過，絕不中止」。索引檔是系統自己的資料：損毀時可以丟棄並重建受影響的部分。

## 2.3 領域模型

領域模型列出系統中的核心概念與它們的關係。全文檢索系統有一套成熟的術語，先把它們定義清楚：

| 概念 | 定義 | 本系統中的例子 |
|---|---|---|
| 文件（Document） | 一個被索引的檔案 | `C:\docs\報告.txt`，有路徑、大小、修改時間 |
| 欄位（Field） | 文件中分開分詞的部分 | 檔名（Name）與內文（Body） |
| 詞元（Token） | 分詞後的最小單位 | `ai`、`模型`、`型研` |
| 詞項（Term） | 查詢時比對的單位 | `term(模型)`、`phrase(ai 模型)` |
| 位置（Position） | 詞元在欄位中的序號 | 片語比對靠連續的位置 |
| Posting | 「某詞出現在某文件、出現幾次、在哪些位置」 | `模型 → (doc 3, tf 2, [5, 17])` |
| 倒排索引（Inverted Index） | 詞 → postings 清單的對照 | 查詢時由詞找到文件 |
| 片段（Segment） | 一批文件的不可變索引檔 | `seg_00000003.lss` |
| 墓碑（Tombstone） | 標記片段中某文件已刪除 | `seg_00000003_000002.lsd` |
| 提交（Commit） | 一組片段構成的一致狀態 | `manifest_0000000007.lsm` |
| 快照（Snapshot） | 讀者看到的某一個提交 | 搜尋期間固定不變 |

```
  Commit (manifest_N) ──1..*──► Segment ──0..1──► Tombstones
                                   │
                    ┌──────────────┼──────────────┐
                    ▼              ▼              ▼
                 Content         Doc          Term dictionary
           (內文長度、雜湊)  (路徑、檔名、     (詞 → postings)
                    ▲         contentRef) ─┐
                    └──────────────────────┘ 可以指向別的片段的 Content
```

### 模型中的一個關鍵發現：文件 ≠ 內容

一開始很自然會把「文件」當成一個整體：路徑加內容。但需求 FR-9 要求「改名或移動時不得重新抽取與分詞，只更新路徑」。

如果文件與內容是同一筆資料，而片段又是不可變的，改名就只能整筆重寫，也就必須重新分詞內文。所以領域模型必須拆成兩個概念：

- **Content**：內文的 postings、長度與雜湊。
- **Doc**：路徑、檔名的 postings、修改時間，以及指向某個 Content 的參照（contentRef）。

改名時，舊 Doc 加上墓碑，新片段寫一筆新的 Doc（新路徑、新檔名 postings），contentRef **指向舊片段裡的舊 Content**。內文完全不用重新處理。

**教學重點**：需求中看似小的一句話，可能改變整個資料模型。分析階段就發現這點，比寫完程式才發現便宜得多。

## 2.4 資料流

系統有兩條主要的資料流。

### 索引路徑（寫）

```
 檔案系統事件 / 啟動掃描 / 溢位後的差異掃描
          │  只標記「這個路徑髒了」
          ▼
 Reconcile：讀取實際狀態，決定 新增 / 更新 / 刪除 / 改名
          │
          ▼
 讀檔 → 編碼偵測 → 抽取文字 → 正規化與分詞（平行）
          │
          ▼
 IndexWriter（單一寫入者）：RAM 中累積 → 寫成片段 → 提交 manifest
          │
          ▼
 背景合併：小片段合成大片段
```

### 查詢路徑（讀）

```
 查詢字串 → Lexer → Parser → 語法樹 → Binder → 詞項樹
                                                │
 快照（固定某個提交）────────────────────────────┤
                                                ▼
                         Executor：逐詞讀 postings → bitset 布林運算
                                                │
                                                ▼
                         BM25 計分 → Top-K → 結果清單
                                                │
                                   選取時 ─► 重新讀檔 → 摘要與高亮
```

兩條路徑的交會點是**快照**。寫入者持續產生新的提交，每個查詢在開始時取得當下最新的快照，之後不受任何寫入影響。第 8 章會詳細說明。

## 2.5 狀態模型：一個檔案的一生

從系統的角度，一個檔案路徑會經歷以下狀態：

```
                 ┌──────────── 事件或掃描 ────────────┐
                 ▼                                    │
 (未知) ──► 待處理（防抖中）──► 處理中 ──┬──► 已索引 ─┤
                                        │            │
                                        ├──► 已跳過（大小、二進位、編碼、隱藏…）
                                        │            │
                                        ├──► 鎖定，稍後重試（1、2、4 秒）
                                        │        └──► 三次後放棄，等下次變更
                                        │
                                        └──► 已刪除（檔案消失或被排除）
```

被跳過或失敗的檔案會寫進診斷紀錄，每個路徑只保留最新的原因。原因種類定義在 `DiagnosticKind`：

```csharp
// src/LocalSeek.Indexing/Diagnostics/DiagnosticsLog.cs（節錄）
public enum DiagnosticKind
{
    TooLarge, Binary, UnknownEncoding, Corrupt, AccessDenied,
    LockedRetryLater, LockedGaveUp, ChangedDuringRead, ReadError,
    LoopDetected, BrokenLink, ReparsePointSkipped, HiddenOrSystem,
    RootUnavailable, WatcherFallback,
}
```

畫狀態圖的好處是**強迫你思考每一個轉換**。例如：已跳過的檔案後來被修正了，診斷紀錄要清除嗎？（要，否則診斷頁的數字會與實際不符，違反驗收標準 #23。）

## 2.6 找出決定架構的難點

分析的最後一步，是從需求中挑出**真正決定架構**的部分。大部分需求（例如「支援 .csv」）只影響局部程式碼；少數需求會影響整體結構。本專案找出七個：

| # | 難點 | 為什麼難 | 影響的設計 |
|---|---|---|---|
| D1 | 正規化會改變長度，但高亮要回到原始座標 | `㈱` 變成 `(株)`、`ﬁ` 變成 `fi` | 分詞器必須攜帶「正規化字元 → 原始範圍」的對照 |
| D2 | 改名不得重新分詞，但檔名本身變了 | 不可變片段無法局部修改 | 文件與內容分離（2.3 節） |
| D3 | 統計值只能算現存文件，不可過時 | 刪除只是加墓碑，片段裡仍有舊資料 | 查詢時由整數精確重算 N、avgdl、df，不預存 |
| D4 | 不可變片段＋墓碑＋背景合併＋快照隔離＋任意中止仍一致 | 多個機制必須同時成立 | manifest 原子提交、檔案參考計數、所有 I/O 經介面 |
| D5 | 合併與增量索引同時進行 | 合併期間發生的刪除與改名不能遺失 | 合併提交時帶入期間的墓碑 |
| D6 | 參考解必須獨立實作分詞與計分 | 共用程式碼就無法互相驗證 | Parser 只產生原始字串的語法樹，分詞在獨立的 Bind 步驟 |
| D7 | 效能：1 GB 文字 4 分鐘、P95 ≤ 100 ms、≤ 600 MB | 三者互相拉扯 | 平行抽取、有上限的 RAM buffer、term-at-a-time 查詢 |

這張表是整份分析最重要的產出。後面每一章的設計，幾乎都能追溯到其中一列。

### D6 的細節：為什麼 Parse 與 Bind 要分開？

一般的查詢處理是「解析時順便分詞」。但需求要求參考解**不得共用分詞程式碼**。如果 Parser 內部就呼叫正式的分詞器，參考解要用 Parser，就等於共用了分詞器。

解法是把流程拆成兩步：

1. **Parse**：只處理語法（括號、運算子、引號），產生的語法樹只包含**原始字串**，例如 `WordNode("AI模型")`。
2. **Bind**：用分詞器把原始字串變成詞項，例如 `PhraseQuery(["ai", "模型"])`。

正式引擎用正式的 Binder，參考解用自己的 Binder 與自己的分詞器。兩者共用的只有語法樹這個**資料型別**。這是「為了可測試性而設計」的典型例子。

## 2.7 風險評估

| 風險 | 可能性 | 影響 | 對策 |
|---|---|---|---|
| Uno.Sdk 在 CI 上無法建置或發佈 | 中 | 高（驗收 #26） | 第一個里程碑就建立 CI，及早發現 |
| 效能達不到 4 分鐘 / 100 ms | 中 | 高 | 及早寫效能工具；正規化走快速路徑 |
| Big5 誤判其他編碼 | 高 | 中 | 加結構檢查；列為已知限制 |
| 監看事件遺失或順序錯亂 | 高 | 中 | 事件只標記髒路徑，實際動作由讀取現況決定 |
| 中斷安全的邊界情況太多 | 中 | 高 | 故障注入測試覆蓋每一個 I/O 操作 |

**教學重點**：風險表要附**對策**，而且對策要能在開發計畫中找到對應的步驟。例如「Uno 在 CI 上的風險」對應到里程碑 M0 就先把 CI 跑起來。事後回顧，這個風險確實發生了（第 13 章）。
